Quill is a 2.1 kB reactive state primitive. It holds a value, tells you when it changes, and gets out of the way. No virtual DOM, no context, no provider tree — and nothing at all to unmount.

Overview

Quill exists because the two common answers to shared state are both too large. React's context forces a re-render of everything below a provider. A global event bus makes data flow impossible to follow. Quill takes the third option: a single mutable cell with a subscription list, one equality function, and a batching boundary.

The whole library is one function, createStore, and four helpers that exist only to make call sites readable. It has no dependencies, no build step, and no opinion about how you render.

Installation#

Install from npm, or drop the ESM build on the page. Quill ships ESM, CommonJS and a single-file IIFE for a <script> tag.

npm install @quill/state
# or, with no build step at all
curl -o quill.js https://esm.sh/@quill/state@1.4.2
iNote

Quill targets ES2019 and above. If you need ES5, use @quill/state/legacy, which is 3.4 kB and drops WeakRef support.

Your first store#

Create a store with an initial value and, optionally, an equality function. Read with get, write with set, and observe with subscribe.

createStore<T>(initial: T | (() => T), options?: { equals?: (a: T, b: T) => boolean, name?: string, devtools?: boolean }) => Store<T>
import { createStore } from '@quill/state'

export const cart = createStore(
  { lines: [], total: 0 },
  { name: 'cart', devtools: true }
)

// read
cart.get().total            // 0

// write — shallow merge
cart.update((state) => ({
  ...state,
  lines: [...state.lines, { sku: 'AX-9', qty: 2 }],
  total: 41.8
}))

// observe; the callback returns an unsubscribe function
const stop = cart.subscribe((next, previous) => {
  console.log('cart went from', previous.total, 'to', next.total)
})
tTip

Always pass a function to update, never a value. Quill cannot tell a value from a function, so a bare function is treated as a lazy initialiser on createStore and as a producer on update.

Derived state#

derive memoises a computation against one or more stores. It recomputes only when a dependency actually changes under the equality function, and it re-runs lazily on read — there is no eager graph to keep warm.

import { createStore, derive } from '@quill/state'
import { cart } from './cart.js'
import { taxRate } from './config.js'

export const totals = derive([cart, taxRate], ([cart, rate]) => {
  const net = cart.lines.reduce((n, l) => n + l.qty * l.price, 0)
  return {
    net,
    tax: Math.round(net * rate * 100) / 100,
    shipping: net > 120 ? 0 : 7.5
  }
})

totals.get()   // { net: 0, tax: 0, shipping: 7.5 }
totals.get()   // cached — no recomputation

A derived store is a full store: you can subscribe to it, and you can use it as a source for another derive. The chain is depth-first, so a diamond dependency resolves once, not twice.

Effects and cleanup#

Effects are the only place Quill touches the outside world. effect runs immediately, then again whenever a dependency changes, and it must return a cleanup function. Cleanup runs before the next run and on dispose().

import { effect, createStore } from '@quill/state'

export const elapsed = createStore(0, { name: 'elapsed' })

const timer = effect(() => {
  const start = performance.now()
  const id = setInterval(() => elapsed.set(performance.now() - start), 250)

  return () => clearInterval(id)   // runs before every re-run and on dispose
})

// elsewhere
timer.dispose()
!Warning

An effect that returns nothing cannot be stopped. If you allocate anything — a timer, a listener, an observer — return a function that releases it. Quill calls dispose() on the store's disposeAll() hook, but it cannot guess what your cleanup should do.

Middleware#

A middleware is a function that receives every write before it lands. Use it for logging, persistence, validation, or devtools. The order of the chain is the order of registration.

import { persist } from '@quill/state/middleware'

persist(cart, {
  key: 'quill.cart.v1',
  // throttle writes, never reads
  throttle: 400,
  serialize: (s) => JSON.stringify(s.lines),
  deserialize: (raw) => ({ lines: JSON.parse(raw), total: 0 }),
  onError: (err, key) => console.warn('[quill] persist failed', key, err)
})

Batching#

New in 1.4. Writes made inside a batch notify subscribers exactly once, after the batch closes, with the final value. This is the difference between 200 renders and 2 when you are hydrating from a server payload.

import { batch } from '@quill/state'

batch(() => {
  for (const row of payload.rows) {
    cart.update((s) => ({ ...s, lines: [...s.lines, row] }))
  }
  session.set(payload.session)
})

// subscribers run once, with the finished state

Async resources#

A resource is a store whose value carries its own lifecycle: idle, loading, success or error. This removes the two booleans and the undefined that every hand-rolled fetch hook eventually grows.

import { resource } from '@quill/state'

export const profile = resource(async (userId, { signal }) => {
  const res = await fetch(`/api/users/${userId}`, { signal })
  if (!res.ok) throw new HttpError(res.status, res.statusText)
  return res.json()
})

profile.load('u_8842')

profile.get()
// { status: 'loading', previous: undefined }
// then
// { status: 'success', value: { name: 'Ines' } }
// or
// { status: 'error', error: HttpError { status: 404 } }

Cancellation#

Every resource receives an AbortSignal and aborts it when a new load supersedes the old one or when the resource is disposed. You never have to write a let cancelled = false flag again.

iNote

An abort is not an error. resource discards aborted rejections, so status stays at its previous value while the next load is in flight.

Design tokens#

State is rarely the only thing that needs to live in CSS. quill/tokens.css exposes every store on :root as a custom property, so a stylesheet can react to state without a re-render.

@import '@quill/state/tokens.css';

:root {
  --quill-cart-total: 0;
  --quill-session: none;
  --quill-theme: light;
}

/* purely declarative — no JavaScript touches this rule */
.checkout[data-busy='true'] {
  cursor: progress;
  opacity: 0.55;
  transition: opacity 180ms ease-out;
}

.checkout__total::after {
  content: counter(total, decimal);
  font-variant-numeric: tabular-nums;
}

Tokens are written on a microtask, coalesced, and only when the serialised value actually changed. A store that settles on the same string writes nothing.

Server rendering#

Quill runs unchanged on the server. There is one rule: create stores once per request, and never at module scope if the value is user-specific.

import { createStore, renderToString } from '@quill/state/ssr'

export function render(request) {
  // per-request, never module scope
  const session = createStore(readSession(request), { name: 'session' })

  const html = renderToString(() => <App store={{ session }} />, {
    // values that must be present in the first paint
    hydrate: { session: session.get() },
    // consumed once on the client, then disposed
    onHydrated: (hydrated) => setTimeout(() => hydrated.dispose(), 0)
  })

  return html
}
!Warning

A store created at module scope in a server process is shared by every request that runs after it. This is the most common Quill bug in production, and it always looks like a caching problem.

TypeScript#

Types ship with the package. The store type is invariant, so a store of number cannot be assigned where a store of number | null is expected.

import type { Store, Derived, Resource } from '@quill/state'

type Listener<T> = (next: T, previous: T) => void

interface Store<T> {
  get(): T
  set(value: T): void
  update(producer: (state: T) => T): void
  subscribe(listener: Listener<T>): () => void
  dispose(): void
}

type Derived<T> = Omit<Store<T>, 'set' | 'update'>

type Resource<T, A extends unknown[]> = Store<ResourceState<T>> & {
  load(...args: A): Promise<T>
  invalidate(): void
}

Error handling#

A thrown error inside an effect propagates to effect()'s error handler and cancels that effect. In development, Quill also logs the dependency list that caused the run, which is usually enough to find the cycle.

effect(() => {
  const chart = mount(chartEl, { data: derived.get() })
  return () => chart.destroy()
}, {
  onError(err, deps) {
    report(err, { dependencies: deps.map(String) })
  }
})

Migrating from 1.3#

Two changes affect almost every call site. First, subscribe now passes (next, previous) instead of a single object. Second, store.set no longer accepts a producer function — use store.update.

npx @quill/codemod v1.4 ./src

// manual fixes the codemod cannot see:
//  · store.set(fn)  →  store.update(fn)
//  · subscribe(v)   →  subscribe((next, prev) => …)

Troubleshooting#

A subscriber runs twice on mount

Effects run once when they are created. If you are seeing two runs, the effect is being created twice — usually because a component body re-executed without disposing the previous effect. Wrap creation in effect() and keep the handle.

Reads inside a batch do not see the write

This is correct behaviour. A batch stages writes; get() inside the batch returns the pre-batch value. If you need the final value mid-batch, read after the batch closes, or use batch.peek().

My equality function is being ignored

equals is only consulted for derived values and for resources. A store's set always notifies. Put the comparison in the producer instead.
